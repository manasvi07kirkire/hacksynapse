# SearchOps backend: implemented boundary and production target

The supplied production vision is the product reference. Its claims that all modules already existed, SQLite was Supabase-ready, reads could remain public, and Tier C could accept a boolean were not valid for this checkout. `docs/BACKEND_AUDIT.md` records the original evidence; this document describes the implemented boundary.

The loops remain `deploy -> observe -> detect -> diagnose -> score -> remediate -> verify -> recover` and `scan -> suggest -> approve/reject/edit -> validate -> one PR`. Detection is deterministic; optional model narration never changes the finding set, severity or evidence.

## Architecture

- Next.js App Router on Node, updated from 14.2 to 15.5.25 with React 19 because patched 14.x releases still had high-severity advisories. Prisma 5 remains; PostgreSQL replaces the prototype SQLite datasource for Supabase and transactional jobs. PostCSS is overridden to the patched 8.5 line.
- API requests use an operator key or an eight-hour HttpOnly session. Distinct per-project API keys restrict read/write access to one project. This is a single-tenant operator installation, **not multi-user SaaS RBAC**. Projects and nested records are scoped explicitly. No invalid selector falls through.
- GitHub App installation tokens are used per project and every repository operation rechecks repository access and default branch. A PAT requires explicit non-production configuration. Webhooks verify raw-body HMAC before parsing. Installation deletion/suspension/removal disables affected projects.
- PostgreSQL jobs deduplicate delivery IDs and project/SHA/analysis-version, allocate deployment numbers with a locked counter, serialize project analysis with expiring leases, retry transient failures three times, and fence expired workers before publication.
- Crawls use bounded Node HTTP requests, DNS-pinned public addresses, same-origin redirects, route budgets and cancellation. Diagnostic manifests are explicitly owner-authorized; SearchOps observes robots/noindex signals rather than treating robots.txt as an access-control mechanism. It does not discover arbitrary off-site links or execute JavaScript.
- Deployed pages must return `X-SearchOps-Sha: <full commit SHA>`. Bounded polling handles short deployment lag. Missing/mismatched markers, incomplete crawls or incomparable history produce `DEGRADED`, never a fabricated healthy regression analysis. `/api/jobs` supports an explicit idempotent recheck after deployment completes, preserving the earlier degraded record.
- One transaction publishes graph, findings, versioned score and final status. Previous snapshots must be completed, strictly older, revision-verified and compatible with the graph version and project configuration. Analysis identity includes origin/manifest/source-map/branch configuration so a change starts a fresh baseline even for the same SHA. Legacy records are quarantined as unverified.
- Ten catalog rules are implemented, with `ORPHAN_PAGE_CREATED` retained only as a legacy type alias. Missing title/meta, invalid schema, duplicates, sitemap consistency, orphan reachability and llms.txt are absolute checks; canonical/noindex/schema removal require a comparable prior page. Every finding stores actual observations; uncertain source attribution is null.
- Scores are deterministic and versioned. Untested citation grounding contributes zero, with `NOT_TESTED` recorded. Citation results measure exact normalized source/answer phrase overlap; they are not search citation probabilities or semantic entailment scores.
- Remediation uses persisted verified findings, exact repository revisions, safe paths, exact patch context, syntax/static rule checks, deterministic branches and PR replay. Static HTML canonical/noindex/schema restoration is supported. Literal TypeScript canonical declarations can produce draft changes; a repository build is explicitly `NOT_RUN`. Unsupported transformations return 422 rather than inventing a patch. Tier B stays draft; Tier C requires an audited operator approval and still must pass source validation. No merge API is called.
- SEO scans capture authorized source, scan provenance and suggestions. URL and same-repository open-PR scans support explicitly mapped static HTML. Applying an approved batch checks ownership, disjoint decisions, edits, exact before text and current base SHA. A batch produces one draft PR. Dynamic page/source adapters, fork scans, sitemap-index expansion and internal-link source transforms need repository-specific implementation/validation; they fail explicitly at their testable boundaries.

## Deployment prerequisites

Local tests use disposable PostgreSQL, a real local HTTP server and faithful GitHub/OpenRouter fakes. This is not live GitHub/Supabase proof. Live operation needs Supabase connections, a GitHub App installation and webhook secret, a deployed version marker, an independently supervised worker and operator monitoring. LLM-requested features additionally need a configured OpenRouter model/key; deterministic Watch analysis persists without narration.

Vercel hosts the APIs; the continuously running worker belongs on a Node worker host. Do not start the worker inside a request or rely on serverless request lifetime. The original Field Manual pages remain labeled fixture previews. `/watch` is the live project view, `/connect` supplies authentication and repository setup, and Advisor/citation calls carry the selected project.
